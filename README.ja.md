# staleness-resistant-docs（日本語版）

> English version: [README.md](README.md)

長く使われる指示ファイル（`CLAUDE.md`、`CONTRIBUTING.md`、運用手順書、オンボーディング文書）で、
**書かれた事実が、誰にも気づかれないまま古くなっていく** 問題への対策です。

やり方は単純です。**事実の記述に「いつ測ったか」と「測り直すコマンド」を持たせる。**
あとは検査ツールが、古くなったものと、そもそも確かめようがないものを教えてくれます。

### このリポジトリに入っているもの

| ファイル | 中身 |
|---|---|
| [`staleness-check.py`](staleness-check.py) | 検査ツール本体。1 ファイル・Python 3.9 以降・標準ライブラリのみ |
| [`EXAMPLE.md`](EXAMPLE.md) | 試しに走らせるための、印付きの記述（コマンドは `echo` だけ） |
| [`tests/`](tests/) | 標準ライブラリだけのテスト: `python3 -m unittest discover -s tests` |
| [`CHANGELOG.md`](CHANGELOG.md) | 版ごとの変更と、その理由 |
| この README | パターンの説明、きっかけになった実例、使ってみて分かったこと |

使い方は、自分の `CLAUDE.md` や手順書の記述に印を付け、CI で、またはファイルを信じる前に、
検査ツールを走らせるだけです。

## 1. 何が問題か

指示ファイルには、こういう記述がたまっていきます。

> テスト: `pytest tests/` — 189件成功、カバレッジ 59.06%（基準の80%に未達）

この文はある時点では正しいものでした。しかし数週間後にはテストは253件になり、
カバレッジは96%になり、基準も満たしています。それでも文章は変わっていません。
そして **その文には「いつ正しかったのか」が書かれていません。**

読む人には、**今の事実と化石の区別がつきません。**

### AI エージェントにとっては、より深刻です

人間なら「なんか古そうだな」と流せます。しかし AI エージェントは `CLAUDE.md` を
**権威ある情報として読み、そのとおりに動きます。**

3コミット前に解決済みの問題に対して、真面目に作業を始めてしまうのです。

### 実際に損害が出た3件

このパターンが生まれた元のリポジトリでの、実例です。

| 古くなった記述 | 実際 | 何が起きたか |
|---|---|---|
| 「カバレッジ 59.06%、基準80%に未達」 | 2日前に解決済み。実際は96.20% | **もう存在しない問題への調査が1件発生した** |
| 「プラグイン 23個中23個が有効」 | 46個中24個が有効、22個が無効 | **合計値が動いていなかったため、見た目に違和感がなく信じられた** |
| 「bats 251件、うち21件スキップ、既知の失敗が最大5件」 | 数週間で889件まで増加 | 「既知のスキップだから無視してよい」という判断を招いた |

**2件目が最も教訓的です。**

日付は比較的新しく、数字も「46個中24個」ではなく「23個中23個」と、
**合計そのものが動いていませんでした。** だから誰も疑いませんでした。

**「日付が新しい」ことは「その数字がまだ正しい」ことの証拠にはなりません。**

## 2. パターンの中身

### (1) 事実の記述に、測定日と識別子を付ける

```markdown
- テストスイート: **253件成功**、カバレッジ **96.20%**
  <!-- measured:2026-07-28 id:pytest-count -->
```

「最終更新日」ではなく **「測定日」** です。文章を手直ししても、事実が新しくなるわけではありません。

### (2) 測定日には、測り直すコマンドを対応させる

````markdown
```staleness-cmd:pytest-count
.venv/bin/python3 -m pytest tests/ -q 2>&1 | tail -1
```
````

**ここが要です。** 日付だけなら「古いかもしれない」としか言えません。
コマンドがあれば、**誰でも（AI エージェントでも）一手で決着をつけられます。**

#### 完全な形: 記述ごとの有効期限と、任意の期待値（v0.2 から）

毎日動く数字もあれば、まず動かない数字もあります。全部を 1 つの `--max-age` で測るのは粗すぎます。
v0.2 からは、記述ごとに有効期限（ttl）を持たせ、コマンドが 1 つの安定した値を出す場合は
その期待値も書けます。

```markdown
- lint は通っている
  <!-- staleness-check: id=lint-status date=2026-11-01 ttl=14d value="0" -->
```

| 項目 | 意味 |
|---|---|
| `id`・`date`・`ttl` | 必須。`ttl` は `<N>d`（この記述を信じてよい日数） |
| `value` | 任意。コマンドの標準出力の期待値。`--run` のとき完全一致で比べます |
| `timeout` | 任意。`<N>s`。記述ごとのコマンドの時間切れ（既定 300 秒） |
| `defer_exec` | 任意。`1` なら、記述が ttl より新しいあいだは `--run` でもコマンドを走らせません（重い測り直し用） |

上の短い形は、そのまま使えます。

### (3) 古くなったときは、黙って直さず「何を損したか」を書く

```markdown
- テストスイート: **253件成功**、カバレッジ **96.20%**
  <!-- measured:2026-07-28 id:pytest-count -->
  > この行は修正が入った後も2日間「59.06%、基準未達」のままで、
  > 無駄な調査を1件発生させました。カバレッジは動きます。
  > この記述を根拠に動く前に、必ず測り直してください。
```

**訂正された値より、訂正されたという事実の方が長く役に立ちます。**
値はまた古くなりますが、「どう古くなるか」という警告は古くなりません。

### (4) その数字が「何を測っていないか」を書く

数字の適用範囲は、数字の一部です。

```markdown
- カバレッジ **96.20%** <!-- measured:2026-07-28 id:coverage -->
  > 測定対象は `apis/` `auth/` `config/` `utils/` のみ。
  > `claude-env/` は1行も測っていません。そして現在の作業はほぼ全て
  > `claude-env/` にあります。この数字を `claude-env/` の品質根拠に使わないでください。
```

これは実際に問題を捕まえました。**健全に見える96%のすぐ隣に、
テストスイートが一度も実行していない、46件が失敗し続けているディレクトリがありました。**

## 3. 検査ツール

```sh
./staleness-check.py CLAUDE.md docs/
```

3 件の記述を持つファイルを、2026-08-31 として走らせた実際の出力（出力は英語です）:

```
CLAUDE.md:2  id=orphan-claim           measured 2026-05-01  (122 days ago) STALE UNCHECKABLE
    claim: - Deployment is session-boundary driven
    - no staleness-cmd block
CLAUDE.md:4  id=pytest-count           measured 2026-07-28  (34 days ago) STALE
    claim: - Test suite: **253 passed**, coverage **96.20%**
CLAUDE.md:6  id=lint-status            measured 2026-08-28  (3 days ago, ttl 14d) ok
    claim: - Lint is clean

3 claim(s) in 1 file(s): 2 stale, 1 uncheckable (threshold: 30 days); 0 malformed, 0 value-mismatch; value-check: ok=0 unknown=0 deferred=0 not-run=1 (pass --run to execute commands)
```

| 表示 | 意味 |
|---|---|
| `STALE` | `ttl`（完全な形）または `--max-age`（短い形）より古い |
| `UNCHECKABLE` | 測り直すコマンドが無い、または同じ id に中身の違うコマンドが 2 つ以上ある |
| `MALFORMED` | 印そのものが壊れている（項目の欠け・日付の誤り・未来の日付）、またはコマンドの囲みが閉じていない。**読み飛ばさず報告します** |
| `VALUE-MISMATCH` | `--run` で、`value=` と違う値が出た |
| `VALUE-UNKNOWN` | `--run` で、コマンドが終わらなかった（時間切れ・起動できない） |
| `VALUE-DEFERRED` | `--run` だが、`defer_exec=1` でコマンドを走らせなかった |

終了コード: `0` `--fail-on` の水準に届く指摘なし ／ `1` 届く指摘あり ／
`2` 測れなかった（対象が無い・読めない） ／ `3` **off**: 印の付いた記述が 1 つも無い。
`3` をわざと `0` にしていないのは、「何も印が付いていない」を「全部新しい」と読ませないためです。

コマンドを実行して、現在の値を記述の隣に並べることもできます。

```sh
./staleness-check.py --run CLAUDE.md
```

## 4. 設計判断 — 「正しいかどうか」は判定しません

似た仕組みは既にあります。Python の doctest、Rust の doctest、mdbook のテストなどです。
**それらは「出力が一致しなければ失敗」と判定します。**

しかしこの用途では、それをやりません。理由があります。

**テストの件数は増えます。出力の書式も変わります。** そのたびに「不一致！」と
言われ続けると、**人はその出力を読まなくなります。** 読まれない検査は、無いより悪いものです。

このツールがやることは3つだけです。

- **古いかどうか** を判定する（日付は客観的なので判定できます）
- **測り直すコマンドが無い** ことを指摘する（これが最も重要な検出です。**誰にも確かめようがない主張**だからです）
- `--run` でコマンドを実行し、現在の出力を記述の隣に並べる（**判断は人間に委ねます**）

「253件成功」と「1131件成功」が同じ健全さを意味するかどうかは、
**文字列の比較で決まる問いではありません。**

> **訂正（v0.2）。** 上の判断は今も既定の動きですが、言い切りすぎでした。
> 終了コードや動かないはずの件数のように、**コマンドが 1 つの安定した値を出す記述**もあります。
> そういう記述では完全一致の比較は安く、正しく働きます。そこで v0.2 では、
> 記述ごとに `value="…"` で比較を選べるようにしました。`value=` の無い記述は、
> これまでどおり出力を並べて人間の判断に委ねます。

## 5. もう一つの設計判断 — 地の文は解析しません

このツールは、**明示的に印を付けた記述しか見ません。**

文章を読んで「どれが事実の主張か」を推測することは、意図的にやめています。
そういう作り方をすると誤検出が積み上がり、やがて出力が読まれなくなり、
その時点でツールは無いより悪くなります。

代償として、印の付いていない記述は見えません。**それでもこちらを選びます。**

**「このツールが何か言ったら、それは読む価値がある」という状態を守ることの方が重要** だからです。

## 6. 使ってみて分かったこと

実際のリポジトリでこのツールを使う中で起きた 4 つの失敗と、今の版での手当てです。

1. **機体ごとに違う数字に完全一致の値を付けると、決着しない。** プラグインの数に `value=` を
   付けました。2 台の機体で正しく数が違ったため、どちらかで必ず赤になり、片方で「直す」と
   もう片方が壊れました。**今は:** そういう記述には日付と ttl だけを付け、`value=` は付けない
   と書いています（`EXAMPLE.md`）。
2. **失敗の形しか出せないコマンドは、成功すると黙る。** 測り直しに
   `grep -oE '[0-9]+ failed, [0-9]+ passed'` を使っていました。全部通ると一致するものが無く、
   「良くなった」が「コマンドが壊れた」と同じ空の出力で返りました。**今は:** 良い状態も
   出せるコマンド（要約の行そのものを取る形）にすること、と書いています。
3. **重い測り直しを push のたびに走らせると積み上がり、外したはずの費用が戻ってきた。**
   テスト全体の再実行が push の検査の時間の大半を占めていました。`defer_exec=1` で記述が
   新しいあいだは飛ばしましたが、記述が古くなった途端に、push のたびに費用が戻りました。
   **今は:** `--no-exec-deferred` で、push の検査からは決して走らせず、手で走らせます。
4. **シェルだけを止める時間切れは、その子を走らせたまま残す。** 前の版は時間切れで起動した
   `/bin/sh` だけを止め、裏に回した孫のプロセスが走り続けました。**今は:** コマンドごとに
   プロセスグループを作り、時間切れでグループごと止めます。テストもあります。

## 7. 導入

```sh
cp staleness-check.py /usr/local/bin/
```

Python 3.9 以降。依存パッケージはありません。テスト: `python3 -m unittest discover -s tests`

CI での使い方の例（確認不能なものがあれば失敗、古いものは警告のみ）:

```yaml
- run: ./staleness-check.py --fail-on uncheckable CLAUDE.md docs/
```

## 8. このツールが解決しないこと

印を付けずに記述する自由は奪えません。また、印の付いた記述が **間違っている** ことを
検出できるのは、その記述が `value=` で完全一致の比較を選んだときだけです。
それ以外で言えるのは「古い」か「確かめようがない」かだけです。

このツールがやるのは **確認のコストを下げること** です。
そして実際のところ、確認が行われるかどうかを決めているのは、そのコストです。
